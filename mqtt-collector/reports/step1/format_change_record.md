# 메시지 형식 변경 대응 기록

## 원칙

수집기 코드(`collector.py`)는 "토픽 → 공간·항목·시각" 변환 규칙을 갖고 있지 않다. 규칙은 전부 `config.yaml`의 `sensors:`에 있다. 그래서 메시지 형식이 바뀌거나 센서가 늘어도 **설정만 고치고 `sudo systemctl restart mqtt-collector`** 하면 대응된다. 재시작하는 몇 초 동안 온 메시지는 브로커가 보관했다가 다시 전달한다(고정 client_id + QoS1 + clean_session=false).

## 사례 1. 센서 시각을 읽는 위치 변경

### 상황

ChirpStack 업링크 메시지에는 시각이 여러 개 들어 있다.

| 필드 | 의미 |
|---|---|
| `time` | 메시지를 처음 받은 게이트웨이의 시계 |
| `rxInfo[].gwTime` | 게이트웨이별 시계 |
| `rxInfo[].nsTime` | 네트워크 서버가 받은 시각 (서버 시계 하나) |

2026-10-20에 수집한 실제 메시지에서 **게이트웨이 `24e124fffef5dccc`의 시계가 서버보다 약 4분 55초 빨랐다.** 같은 메시지를 다른 게이트웨이 `24e124fffef79304`도 받았는데, 그쪽은 서버와 0.04초 차이였다.

```
센서 EM300-TH-151547 (실습실, 중앙 우측)
  time                 : 2026-10-20T07:33:20.761+00:00   ← 첫 게이트웨이(dccc) 시계
  rxInfo[0] (dccc) gwTime 07:33:20.761 / nsTime 07:28:25.356   차이 +4분 55.4초
  rxInfo[1] (9304) gwTime 07:28:25.321 / nsTime 07:28:25.358   차이 -0.04초
```

`time`은 "처음 받은 게이트웨이"의 시계라서, 어느 게이트웨이가 먼저 받았느냐에 따라 같은 센서의 시각이 메시지마다 약 5분씩 앞뒤로 튄다. 실제로 같은 센서 `EM300-TH-151836`이 한 번은 dccc가 먼저 받아 `time`이 5분 빨랐고, 다음 번에는 9304가 먼저 받아 정상이었다. 30건을 받은 표본에서 센서 메시지 15건 중 **6건(40%)이 dccc가 먼저 받은 메시지**였다.

### 영향 (변경하지 않았다면)

- 센서 메시지의 약 40%가 실제보다 약 5분 **미래 시각**으로 저장된다.
- 같은 센서의 데이터 순서가 뒤섞여서, 1분 단위 커버율과 과제 3의 60분 예측, 과제 5의 일정 결합이 틀어진다.
- 이 오차(295초)는 당시 안전장치 기준(수신 시각과 300초 이상 차이 나면 수신 시각으로 대체)보다 작아서, **경고 없이 그대로 저장**됐을 것이다.

### 바꾼 것 (`config.yaml`만, 코드 수정 없음)

```yaml
# 변경 전
    time: {path: time, unit: iso}

# 변경 후: 서버 시각을 우선 쓰고, 없으면 time
    time: {path: [rxInfo.0.nsTime, time], unit: iso}
```

```yaml
# 안전장치 기준을 좁힘: 300초 → 120초
defaults:
  max_clock_skew_s: 120
```

### 확인

변경 후 dry-run 결과(2026-10-21 10:22, 실습실 센서):

| 센서 | 항목 | delay_ms (수신 − 저장 시각) | time_src |
|---|---|---:|---|
| EM320-TH-389818 | 습도, 온도 | 234 | sensor |
| EM300-TH-151606 (중앙 좌측) | 습도, 온도 | 235 | sensor |
| EM300-TH-151547 (중앙 우측) | 온도, 습도 | 248 | sensor |

- 모든 센서 줄의 지연이 0.23~0.25초로 일정해졌다. 5분 어긋남이 사라졌다.
- 센서 시각을 쓰지 못해 수신 시각으로 대체한 건(`time_src="recv"`)은 0건이었다.
- 서비스 재시작 후 health 로그에서 `parse_errors` 0, `write_errors` 0이었다.

## 사례 2. 저장 범위 변경: 공간·항목 필터 추가

### 상황

브로커에는 과제에 필요 없는 데이터도 함께 들어온다.

- 환경 센서: 실습실, 사무실, 사무실 밖. 항목은 온도, 습도, CO₂, 기압, TVOC, 조도, 적외선, 소음, 배터리 등.
- 냉난방(xflow): 대표실 실내기·실외기, 개발실 실내기·실외기, 사무실, 회의실, 집중회의실, 컨트롤러.

과제에서 일정 자료와 맞춰 쓸 곳은 **실습실(수업 시간표)과 회의실(회의실 예약)**이고, 항목은 **CO₂·온도·습도**다.

### 바꾼 것 (`config.yaml`만, 코드 수정 없음)

```yaml
  # 환경 센서 규칙에 추가
    only_tags:
      space: [실습실, 회의실]
    only_items: [co2, temperature, humidity]

  # 냉난방 규칙에 추가
    only_tags:
      space: [실습실, 회의실]
```

### 확인

- 필터 적용 후 dry-run(2026-10-21 10:22)에서 `sensor` 줄은 전부 `space=실습실`이었고 항목은 온도·습도뿐이었다. 사무실 센서, TVOC, 배터리, 기압은 저장되지 않았다.
- 서비스 가동 후 health 로그(10:33~10:37)를 보면 분당 메시지 16~21건 중 10~13건이 `no_items`(필터로 제외)였고, 11~24건이 저장됐다. `write_errors`는 0이었다.
- 회의실에는 CO₂·온도·습도 센서가 없어서 냉난방 전원(`power`)만 저장된다. 회의실 예약과 냉난방 전원을 비교하면 노쇼나 빈 방 냉난방을 찾는 데 쓸 수 있다.

## 새 센서가 추가될 때

측정값은 `auto_items: {path: object}`로 `object` 안의 숫자를 전부 읽는다. 그래서 같은 ChirpStack 애플리케이션에 새 센서가 붙으면 설정 변경 없이 저장된다. 필터 목록에 없는 항목이나 공간이면 목록에 이름만 추가하면 된다. 예를 들어 TVOC도 모으려면 `only_items: [co2, temperature, humidity, tvoc]`로 바꾼다.

## 설정만으로 안 되는 경우 (한계)

- payload가 JSON이 아닌 바이너리(protobuf)이거나, 값이 JSON 문자열 안에 또 JSON으로 들어 있는 경우. 예를 들어 ChirpStack v3의 `objectJSON`이 그렇다.
- 공간 이름을 여러 태그 중 있는 것으로 골라야 하는 경우. 시각과 항목은 경로 목록(`[a, b]`)을 지원하지만, 태그는 아직 경로 하나만 지원한다.
